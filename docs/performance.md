# Performance

There is no fixed latency target. A command's duration includes process startup, source discovery, synchronous refresh, database inventory snapshots, matching and output serialization. A warm index avoids unchanged transcript parsing, but does not avoid source enumeration or all database copying.

## What determines cost

ASCII literals of at least three characters use FTS5 trigrams plus conservative candidates for Unicode/NUL correctness. In the final synthetic run, 6,000 of 60,200 search documents (9.97%) contained non-ASCII text and were eligible for the case-insensitive fallback union. Short/non-ASCII literals and regexes scan cached search documents. Their median overhead relative to the ASCII query was about 0.092–0.119 seconds. The real subset had 24.22% non-ASCII documents and roughly 0.004–0.019 seconds of median fallback-query overhead. These are end-to-end comparisons with different match sets and uncontrolled variance, not isolated matcher microbenchmarks.

An unchanged OpenCode refresh still privately snapshots and enumerates the database to prove its complete inventory. The final synthetic OpenCode-only refresh took median 0.031 seconds for a 4,530,176-byte source DB and 50 reused sessions; the final real OpenCode inventory took 0.206 seconds for 251 reused sessions. These include startup, index opening, snapshot, enumeration and refresh; snapshot copy time is not isolated. Cursor chat snapshots are reused within a refresh and skipped when dependencies are unchanged.

A changed plain Claude, Codex, Droid or Pi transcript that only grew parses just its new tail, after hashing its already-indexed prefix to confirm it is unchanged, so an incremental refresh still reads each changed transcript once. Cursor transcripts, compressed Codex rollouts, and rewritten, truncated or replaced files are reread fully. Every changed OpenCode backing database conservatively invalidates its sessions. Partial/malformed files are retried and stay incomplete; a "warm" run over live or unhealthy stores may therefore still parse data. Queries sharing one index read concurrently; refreshes serialize under an exclusive writer lock, and a query that waits more than 5 s for it answers from the last published index with exit 1. Output size, storage speed, source count, large transcripts, concurrent writers and Unicode candidate fraction affect latency.

The final synthetic index occupied 115,949,568 bytes for 22,080,376 bytes of discovered source files. Original text, normalized search documents, FTS postings and SQLite overhead all contribute. This ratio is specific to repetitive synthetic data. Disk capacity must be checked before indexing real stores; deleting a stopped index recovers the space at the cost of a cold rebuild.

## Scope of evidence

The benchmark records individual samples and medians, with a fresh index for cold measurement and one discarded warmup before each query series. "Cold" means no slimetrail index, not a flushed OS filesystem cache. It runs one CLI process at a time; no throughput or concurrent-load claim is made. Cold and changed-source cases are single observations. Warm samples include refresh, and query stdout goes directly to the null device with snippets disabled.

See [recorded runs](tests/search-performance/README.md#recorded-runs) for real-store coverage and any timeouts. Real-store metadata dimensions can include companion/unsupported files and are not a count of parsed sessions. Real measurements never modify source files, never open original DBs through benchmark SQLite code, and never retain source-containing benchmark indexes. Linux runtime performance has not been established by this local macOS run.
