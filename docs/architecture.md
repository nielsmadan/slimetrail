# Architecture and privacy

The CLI captures environment, current directory, clock and IANA time zone once. Core functions receive a `Context` and explicit options. Refreshes take `RefreshOptions`: a mode (`RefreshMode::Query` or `Full`), the writer-lock wait, a build policy and an optional `Observer` that receives `RefreshEvent`s (waiting, rebuild progress, ingest progress). The library writes nothing to stderr; the CLI renders those events. The Rust library is an implementation seam; the external compatibility boundary is [CLI JSON v1](json-protocol.md), not serialized internal models. There is no Python import API.

## Design rationale

The project centralizes format knowledge previously duplicated across ringleader, check-agent-logs and time-reconstruct. The November 2026 design replaced repeated raw-file searches with a disposable incremental index: the initial investigation reported an all-agent search taking minutes on 2026-11-15, superseding a September assessment based on a 3.5-second scan of a smaller corpus. These are historical motivations, not slimetrail performance measurements; see [measured results and limitations](performance.md).

Rust was chosen to reduce parsing and process-startup overhead. External consumers use versioned subprocess JSON, following ringleader's hooklinesinker integration model, so Python consumers need neither a stable Rust API nor platform-specific PyO3 wheels. Shared synthetic expected outputs constrain compatibility while Python readers coexist with the Rust implementation. [Integration boundaries and reference readers](integrations.md) describe the migration seam.

The initial alternatives review, dated 2026-11-15, found `@tangle-network/harness-sessions` lacked Cursor support and search/indexing; ATXF (`leostera/atxf`) addressed transcript exchange; and `coding_agent_session_search` and `agent-sessions` coupled their readers to application search stacks outside this project's scope. This records the original selection rationale, not a current capability survey. V1 uses SQLite FTS5 with synchronous refresh and literal/regex matching; fuzzy search, embeddings, a daemon and file watching remain outside scope.

The November 2026 first-indexing revision kept synchronous refresh and made it cheap and honest instead of replacing it. Its governing rule: a session the user remembers must never be silently missing from an exit-0 result, so every limit on coverage either makes the response incomplete (exit 1) or, for the deliberate `compact` coverage preset, carries an informational diagnostic. Rejected alternatives: time-budgeted partial results (silent first-use misses), a detached background build (agent sandboxes kill it), a pure scan without an index (does not work for database-backed stores) and a JSONL hybrid scan (its failure mode is silent exit-0 misses). The revision has three parts: keep-warm refreshes (trusted private snapshots, append-only transcript parsing, per-session Devin change keys, concurrent readers with one writer), indexing less (stored text separate from searchable text, one index-wide coverage) and an explicit build gate (per-agent estimates; small jobs build inline, larger ones prompt on a terminal or report `index_required`). OpenCode was deliberately left out of that revision: it still invalidates every session on any database change, and its 2.x tables are not read. Defaults must hold for any mix of agents and any corpus size; a measurement of one local corpus is a labelled stress case, not a tuning target.

The OpenCode work deferred from that revision has two parts. First, a per-session change key like Devin's, built from `session.time_updated`, the message and part counts, the maximum `time_updated` over messages and parts and, on 2.x, the maximum `seq`; deleted sessions are found by diffing the session set, and `slimetrail index` sweeps content to catch edits that bypass the ORM's `$onUpdate` and leave `time_updated` unchanged. OpenCode indexes no `time_updated` column, so a whole-database aggregate is a table scan (about 3.2–3.7 s on a 4 GB database); narrow it through the `(session_id, time_created, id)` message index and the `part` session index first. Second, a 2.x reader for `session_v2`, `session_message` (unique on `session_id, seq`) and `session_part`, mapping parts as the 1.x reader does: text to `message`, reasoning to `meta`, everything else to `tool`. Keep the 1.x reader until a 2.x release is marked Latest on GitHub (on 2026-11-25 that is still `v1.19.6`, although v2.4.1 has shipped). 2.x migrates 1.x data in place (`packages/core/src/database/v1-migration.bun.ts` in `anomalyco/opencode`), so 1.x support can be removed after that. OpenCode 2's own search index (`packages/core/src/session/search-index.ts`) indexes only user, assistant and compaction messages, caps each column at 64 KiB and uses a contentless FTS5 table.

## Refresh and query lifecycle

`src/api.rs` opens one `IndexSession`, refreshes selected agents, then queries from the same session. Every session holds the non-versioned `lifecycle.lock` shared for its lifetime, so concurrent invocations read side by side. Opening first tries the lock exclusively, once and without waiting; only when that succeeds, so no other slimetrail process (including an older binary, which holds it exclusively) is running, does it prune older index files and remove legacy `staging/slimetrail-snapshot-*` and stray `staging/tmp-*` directories before taking the shared lock. Without a writer, the index database is opened read-only, and an index that does not exist yet reads as empty.

Writes need the exclusive `writer.lock`, a 0600 file with the same checks as the lifecycle lock. The refresh code takes it itself and holds it only for discovery and writes; the read-write connection exists only inside that guard, so no public method can write without it. With it held, the schema is created inside `BEGIN IMMEDIATE`, re-reading `user_version` in the transaction. Each refresh first increments the index-wide `settings.refresh_seq`, before it discovers anything, and each agent's finish records `published = generation` and the run's sequence number alongside its status. A query records `refresh_seq` at the start of each refresh, then waits up to 5 s for the writer lock. If it gets it and every selected agent was published by a refresh that started after that point, it skips its own refresh and reuses those runs' stored diagnostics; otherwise it refreshes. Either way it checkpoints the WAL best-effort (`TRUNCATE`), then opens a read transaction and pins its snapshot before releasing the lock, so all of its reads see one published state. A query that cannot get the lock in 5 s answers from the last published state inside one read transaction, with `incomplete: true` and a `refresh_in_progress` diagnostic, or `coverage_rebuild_pending` while a coverage rebuild is unfinished (also when it does get the lock). `slimetrail index` waits up to an hour. A wait is reported to the observer as `RefreshEvent::Waiting`; the CLI prints `waiting for another slimetrail refresh…` only for `slimetrail index` with stderr on a terminal. Full refreshes (`RefreshMode::Full`, used by `slimetrail index`) do not pin a snapshot; only query refreshes do. Apart from that wait timing out, an index-busy error can only come from the 5 s shared `lifecycle.lock` wait at open, which an older binary holding the lock exclusively (or a session pruning old index files) can cause.

Each session stages its private snapshots in its own directory: it creates `staging/tmp-<random>/` (0700), creates and exclusively locks `owner.lock` (0600) inside it, then renames the directory to `staging/proc-<pid>-<random>/`. When the session closes, the directory is removed if it holds nothing but `owner.lock`; otherwise it is left for a later sweep. At open, a `proc-*` directory whose `owner.lock` can be locked belongs to a dead process and is removed; one without `owner.lock` is left alone. Different indexes have independent snapshot staging.

`src/sources/` discovers identities before emitting entries. Native header/row identity wins over a filename guess. Each `Entry` has a dense display index and a `source_id` based on a native identity plus emitted-item ordinal, or physical-record ordinal plus emitted-item ordinal. These are stable on unchanged reread and append, not across arbitrary rewrites. Parent provenance is optional when the store only establishes automation/subagent status.

Discovery includes native archives and child sessions. Codex discovery also reads the `<name>.jsonl.zst` rollouts Codex compresses when idle, decoding every zstd frame while reading; a plain `<name>.jsonl` beside one is the session and the compressed copy is ignored. Duplicate session identities prefer the live source, then newer source mtime, then deterministic path order. Every JSONL reader walks the shared ringleader archive and keeps only transcripts whose positive format marker names its own agent (Codex `session_meta`, Droid `session_start`, Pi `session`, Cursor untyped records with a top-level `role` and a `message` object, Claude message/title records), so one label folder can mix agents without mislabelling. An archived Cursor transcript reads its metadata only from the chat directory named after it (`<id>/meta.json`, `<id>/store.db`), so a Claude companion directory is never consulted as a Cursor chat. A file whose first identifying record is foreign but names no agent, or that is ambiguous/malformed, is diagnosed once, by the Claude reader (by the Codex reader for a compressed `.jsonl.zst`, which only Codex reads), and never attributed.

The index fingerprints file dependencies using device, inode, size, nanosecond mtime and ctime, including companion-file presence. Droid settings, Cursor metadata and database sidecars participate. Devin's fingerprint is a per-session change key, not file metadata. Codex title records are parsed once per observed title-file fingerprint into a shared immutable final-title map; later records, including empty titles, win. A Codex session's fingerprint covers its own transcript plus a hash of only its own final title from that map (a separate `title_mark` field), not the title file's stat, so a new thread appended to `session_index.jsonl` leaves every other Codex session reusable, and a rename invalidates only the renamed session. A title file that cannot be read is read once more; if that also fails, each session keeps the title hash from its cached fingerprint (sessions without one get an unavailable marker), so nothing is invalidated, and discovery adds one `source_unavailable` diagnostic for the agent; sessions reparsed meanwhile may lack titles and are stored for recheck (see append mode below). Malformed title records are likewise reported once per refresh as an agent-level `malformed_metadata` diagnostic, not on each session, so the run stays incomplete while they persist. Available root prefixes are canonicalized; missing or inaccessible suffixes retain their lexical identity. All roots are serialized and SHA-256 hashed into a namespace. Source availability is diagnosed only for selected agents, so an inaccessible unselected store does not abort healthy queries. Every source/session/entry/document relationship includes namespace and owning source, so identical IDs from different roots cannot mix. Namespace garbage collection is deferred; removing the index remains a full reset.

Refresh covers the selected agents before cwd/date/kind filtering. It discovers all of them first and estimates each agent's pending work (see [build estimates](performance.md#build-estimates)); the gate (`estimate::gate`) then decides from those estimates alone. Under a build limit with per-agent admission (`BuildPolicy::Limit` with `Admission::PerAgent`, used by non-interactive queries and by an interactive query the user declined to build), agents are admitted smallest first while the total estimate fits; the others are left unrefreshed with an `index_required` diagnostic and answer from their last published state. When no admitted agent has pending sessions and no selected agent was ever published, nothing is refreshed and the API returns an incomplete envelope with the command's empty data. All-or-nothing admission (`Admission::AllOrNothing`, used by interactive CLI queries) instead fails with `Error::IndexRequired`, carrying the estimate of every agent with pending work, as soon as any agent does not fit, whether or not it was published, so the CLI can prompt before any session is indexed. `BuildPolicy::Inline`, the `RefreshOptions` default and what `slimetrail index` uses, admits everything. The writer-lock wait and an unfinished coverage rebuild answer from the published state before the gate and never fail this way. The gate runs before any source, session or entry row is written, but not before every write: by then the writer has created the schema if needed, persisted the effective coverage and incremented `refresh_seq`. Discovery's private snapshots are released once the gate has decided. Gated agents' snapshots are dropped, and each admitted agent after the first whose discovery holds snapshots is discovered again just before its ingest, so one agent's database copies are not kept alive while another agent parses; the progress totals follow the new estimate. After each agent's ingest, the summed time of its successful source ingests (parse and write) and the bytes they parsed are added to the `throughput` table under the coverage the ingest ran at, when at least 1 MiB was parsed; a failed or churning source adds nothing, and a rejected append resume that fell back to a full parse counts the whole transcript. The coverage a build uses is decided in one place: the index's stored coverage once any agent has a published generation, any source is stored or a coverage rebuild is pending, and otherwise the caller's coverage, so the first build's coverage choice applies. Unchanged sources reuse parsed entries. Changed sources are reparsed one at a time, streaming into a transactional savepoint; a transcript whose reader stored an append state and that only grew resumes where its last parse stopped (see append mode below). A source is reused only when its cached identity, dependency list and fingerprint equal the ones discovery just observed and discovery attached no private snapshot to it, since an attached snapshot is a reader's request to reparse; the live dependencies are not fingerprinted again. A source stored for recheck is never reused, and `slimetrail index` also rechecks an append source whose prefix a query refresh only spot-checked. A partial source with an unchanged fingerprint is reused like a fresh one and its stored diagnostics are replayed, so the result stays incomplete until the source changes. Database dependencies are trusted at ingest, because the private snapshot's acquisition checks are their consistency boundary. A reader names its live transcript through `Source::transcript` (the JSONL readers for Claude, Codex, Cursor, Droid and Pi do), and that file is still checked: it is stat'ed just before and just after the parse, and is stable only if its device and inode are unchanged and it either grew or kept the same size, mtime and ctime. A same-size in-place rewrite, a truncation, a replacement or a removal is a change, as is a parse whose identity differs from discovery's when `Source::drifted` reports that the source's dependencies changed since discovery; otherwise such a parse fails. Cursor's transcript is checked even though its database is snapshotted. A change retries once, at the same source path or else at the rediscovered source of the same identity (so a Codex rollout decompressed mid-refresh is reread from its plain file); repeated churn rolls back and marks coverage incomplete. A transcript appended during its parse is stored as stable with the discovery-time fingerprint, so the next refresh picks up the rest. Stable malformed sources may publish their good entries with persistent diagnostics. Failed old rows are retained for recovery but excluded from current query results.

Append mode applies to uncompressed Claude, Codex, Droid and Pi transcripts, whose shared JSONL reader stores a `SourceState::Append` with each parse. It records the length of the transcript's complete, newline-terminated prefix, a SHA-256 digest of each 1 MiB chunk of that prefix (`PREFIX_CHUNK`), whether the prefix was last only spot-checked, its line, entry and malformed-line counts, the file's device and inode, a fingerprint of the companion files whose change forces a full reparse (Droid settings), and the session metadata as of that boundary. `sources.state` holds it in a versioned envelope; a state that does not decode or has another version means a full reparse. When a source with an append state is not reused, refresh hands the state to the reader. The reader opens the transcript once and resumes only if the device and inode match, the file is at least as long as the prefix, the companion fingerprint is unchanged, and the chunks it checks, read through that handle, hash to their stored digests. A query refresh checks the first chunk and the chunks overlapping the last 1 MiB of the prefix: a prefix of up to 2 MiB is checked in full, and a longer one costs at most 3 MiB of hashing however long the transcript grows. `slimetrail index` checks every chunk, and also resumes (with a whole-prefix check) every source whose prefix was only spot-checked, even when its fingerprint is unchanged. That is a deliberate trade-off: an in-place rewrite confined to the unchecked middle of a prefix longer than 2 MiB, in the same file and not shrinking it, is not detected by query refreshes, which keep the entries indexed from the old bytes until `slimetrail index` finds the mismatch and reparses the transcript in full. On success the reader parses only the tail and numbers entries after the stored count. The index deletes only the entries at or after that count and the native-title document, updates the session row in place, and writes the new state in the same savepoint. Any mismatch is rejected before an entry is emitted, and a resumed parse that fails for any other reason is rejected as well; the savepoint rolls back and the source is reparsed in full. A final line without a newline is parsed and indexed but left out of the state, so it is reread once completed. A final line without a newline that is not valid JSON is skipped while the file was modified less than 10 minutes before the command started (`Context.now_ms`), and the parse sets `recheck` without a diagnostic. Readers set `recheck` whenever a parse result depends on something outside the session's fingerprinted dependencies: besides such a recent torn line, an unreadable Codex title index and unreadable Cursor `store.db` metadata. A source stored for recheck is visible but never reused, so each refresh rereads it (resuming when it has an append state) until the line is completed or old enough to count as malformed, or the metadata is readable again. The torn-line rule also applies to Cursor transcripts and, through the title index, to every Codex session parsed while the title index ends in such a line. Codex index titles are reapplied on every parse, so a title change resumes with no new bytes. Compressed `.jsonl.zst` rollouts and Cursor transcripts always reparse in full: Cursor's last entry takes a fallback timestamp from metadata and its `store.db` changes constantly.

Each agent's refresh generation is bumped, and persisted as incomplete, only after its discovery succeeds and before source changes commit. A discovery that fails outright leaves the generation and the visible sources untouched and records the failure diagnostics with status incomplete, so the previous state stays queryable with `incomplete: true`. A source is visible when its status is fresh or partial and its generation is at least its agent's last published generation, so a killed run never hides the rows it already replaced. A normal read comes after the process's own refresh (or a coalesced one) and therefore sees one published generation. A stale read, which is always exit 1, may also see sources that another live run has already replaced. Only complete discovery permits deletion of missing sources. When enumeration is incomplete, fresh and partial sources not seen in the run whose generation is at least the published one are moved up to the new generation at the end of the agent's run, so a source a partial inventory omitted stays visible. A restart refreshes again before querying, so interrupted ingestion does not silently present mixed generations as complete. Source modules receive cache metadata and never open the index.

## Index storage and search

The current file is `index-v3.sqlite3`, created with `auto_vacuum=INCREMENTAL` before any table and kept in WAL mode, so the `-wal` and `-shm` sidecars sit beside it. Every connection uses `synchronous=NORMAL` (corruption-safe in WAL, and the index is disposable), `foreign_keys=ON`, `secure_delete=FAST`, a 64 MiB `journal_size_limit` and a 30 s busy timeout. `secure_delete=FAST` zeroes deleted content on the b-tree pages it occupied when that costs no extra I/O, and every refresh that writes ends with `PRAGMA incremental_vacuum`, which removes free pages from the file, so deleted transcript text does not linger in the database file's free pages. Schema/parser/search-normalization changes can require a new index version; this version is independent of JSON protocol version 1. Within a version, `PRAGMA application_id` marks the table layout. A v3 index with an older layout, left by an unreleased development build, is deleted at open and rebuilt when no other slimetrail process holds the lifecycle lock; while one does, commands fail with exit 2 and say so. A non-versioned `lifecycle.lock` covers all versions. Only exact recognized older index filenames and their sidecars are pruned, only when no other slimetrail process holds the lifecycle lock, and only once the current index holds a visible published session, so a rollback to an older release keeps its index until the new one has data; sidecars go before their database. Newer versions are preserved. Active databases are never unlinked or renamed.

Entries hold original text, which `read` and `entries` return in full. Each entry also records whether it is ordinary text, a tool result, or a duplicate (Claude's string `toolUseResult` repeating the same record's `tool_result`). A tool result's text is stored split in two columns whatever the coverage: `text` up to its last 2 KB and `text_tail` after it, with `tail_start` recording the split; reads concatenate them. That stored text is distinct from the searchable text. `src/index/coverage.rs::searchable_start` decides, per coverage, whether an entry is searchable and from which byte offset. A search document stores that offset as `text_start`, plus flags for non-ASCII/NUL data in the searchable slice `text[text_start..]`, but no copy of the text. Native titles produce one search document per session, with `text_start = 0`; derived titles do not. The FTS5 table is contentless (`content=''`, `contentless_delete=1`). The writer inserts the ASCII-lowercased slice into it directly, so the index holds trigram postings but no normalized copy of the searchable text. A delete trigger on search documents removes their postings, including for cascaded deletes. `verify_integrity` runs SQLite's integrity, foreign-key and FTS5 integrity checks and checks that documents and FTS rows have equal counts. It then takes a deterministic sample of up to 100 documents, evenly strided by `document_id`, recomputes each one's searchable slice from its entry or title, and checks its non-ASCII and NUL flags, the entry's stored tail split and that its first trigram matches. The document child-key index includes entry index, avoiding growing per-session scans during deferred foreign-key checks.

Coverage applies to the whole index and is stored in the one-row `settings` table. A new index takes the configured coverage. After that, queries use the index's stored coverage even when the config differs. They never rebuild for coverage; searches report the difference with an informational `coverage_mismatch` diagnostic. Only `slimetrail index` reconciles the index to the config. Under the writer lock and before its refresh, it first records `coverage_pending`. It then clears FTS with `'delete-all'` and empties the search documents in one transaction with the delete trigger dropped and foreign keys off, so SQLite can truncate the table instead of deleting row by row, and recreates the trigger. It recreates the documents from stored entries and native titles, committing every 10,000 rows or 64 MiB of text and reporting `RefreshEvent::Rebuilding` progress. Finally it sets `coverage` and clears `coverage_pending` in one commit, then runs `PRAGMA incremental_vacuum`. No transcript is reparsed; the rebuild counts toward the run's `elapsed_ms` but not toward any build estimate. While `coverage_pending` is set, no refresh except the one completing the rebuild writes anything, including `RefreshMode::Query` library refreshes. Queries and those refreshes report a `coverage_rebuild_pending` diagnostic with `incomplete: true`, and query results may be missing matches because the search documents are partly rebuilt. The next `slimetrail index` restarts an interrupted rebuild from the beginning.

ASCII literal queries of at least three characters use a safely quoted trigram candidate query. Case-insensitive matching unions all non-ASCII documents into the candidates; both case modes union NUL-containing documents. Short, non-ASCII and NUL literals, and arbitrary regexes, scan indexed documents; a compact tool-result document reads only the stored tail. Both paths verify, count and build snippets on the same searchable slice of the original text. Rust regex verification of that slice is the final authority, including Unicode simple case folding. There is no hand-maintained folding map or speculative regex prefilter. The library resolves `CaseMode::Smart` before choosing candidates; a regex query is parsed once with regex-syntax, which both decides smart case and finds a trailing verbose-mode comment. Whole-word matching wraps the verification regex in half word boundaries without changing candidate retrieval: a whole-word literal match is always a substring match, so the literal candidate set must stay a superset under any future candidate scheme. Unicode word-boundary assertions push the regex crate off its lazy DFA for non-ASCII text, so each document is first checked with the unwrapped regex and only matching documents run the wrapped one.

Candidates stream in one global pass ordered by session/document. FTS rowids and indexed Unicode/NUL subsets form a union before original-text joins; eligible session keys and kind filters apply before text hydration, with native titles preserved. Fallback scans traverse the session index, reject ineligible keys and kinds before text hydration, and sort document order within each session; temporary text sorting is bounded by the largest accepted session rather than the whole eligible corpus. Ranked results remain bounded. Read pages stream entries but must visit the complete rendered session to calculate `total_chars`. Timeline selects event metadata only, retaining in-window events and missing-timestamp counts without loading entry text. See [performance](performance.md) for measured costs.

## Private SQLite snapshots

Original agent databases are **never opened through SQLite**, even with `mode=ro`: SQLite could create or modify native sidecars. Instead `src/sources/sqlite.rs` retains read-only OS handles for the DB/WAL and observes SHM/rollback-journal metadata. It captures all pre-copy identities and timestamps, then copies the DB and WAL with `std::fs::copy`, which tries an APFS clone (`fclonefileat`) on macOS and `copy_file_range` (a reflink on btrfs/XFS) on Linux. A copy whose length differs from the captured length is rejected as changed during copy. `fs::copy` reopens the source by path, so it is not tied to the retained handles; the post-copy check compares both the path's and the retained handles' identities and timestamps with the captured ones, which detects a replacement made before or during the copy. Length mismatches, replacements or churn reject the attempt; it retries once. Source SHM contents are never copied.

Accepted copies live in fresh 0700 directories under the session's own staging directory, with 0600 files. `fs::copy` carries the source's mode across, so each copy is set to 0600 immediately; the 0700 directory protects it in between. SQLite opens only the private copy read-write for WAL recovery, then enables `query_only`; its locks and sidecars stay private. Shared snapshot handles let all changed sessions from one backing database use the same accepted copy. A snapshot disappears when the last discovery or session holding it is dropped: right after the build gate for agents not ingested next (see refresh above), otherwise after the agent's ingest. Startup removes only abandoned staging in that index's staging directory (see above), never global temporary directories.

Clean rollback-mode databases are supported; a nonempty rollback journal is rejected rather than attempting potentially unsafe recovery, including recovery involving original master-journal paths. This is metadata-validated quiescence, not an atomic OS snapshot or protection against adversarial metadata forgery. A continuously changing source can remain unavailable.

OpenCode and Devin always snapshot and enumerate their inventory, even on an otherwise unchanged refresh, then reuse unchanged entries. Cached sessions alone cannot prove complete inventory. A future shortcut requires a persisted completeness proof.

OpenCode keeps the whole-database rule: any change to its database reparses every session, because aggregate row counts or maximum timestamps are not sufficient evidence against same-size edits. Devin alone relaxes that rule. Its discovery reads a per-session change key from the snapshot in one pass: the session's `message_nodes` row count, maximum `node_id` and maximum `rowid`, plus its `sessions` row (title, working directory, creation time, `last_activity_at`, `main_chain_id`); a subagent child `ID/AGENT` uses its parent's key plus its `subagent_heads` `chain_node_id` and `updated_at` when that column exists. The source fingerprint is the SHA-256 of that key, so only sessions whose key changed get the snapshot and are reparsed. Each Devin parse also stores a content hash in `sources.state`, covering every `message_nodes` column the parse reads for the rows it loads plus the `sessions` row and, for a child, its head row. Query refreshes trust the change key. `slimetrail index` additionally recomputes the content hash of every session it would otherwise reuse and reparses any whose hash differs, so an in-place edit that leaves the change key unchanged is picked up only by `slimetrail index`.

## Security boundary

The index contains private session data and possibly secrets. Index directories must be 0700 and files, locks and journals 0600. Existing insecure, symlink or multiply linked index files are rejected. Canonicalized paths reject source/index overlap in either direction. Discovery avoids recursive symlink traversal into unrelated stores. Core diagnostics omit entry text, but ordinary query output intentionally includes transcript data and identifiers.

Tests use synthetic fixtures. The opt-in real benchmark uses a separate private repo-local index, emits only aggregate metrics, discards search stdout, sanitizes stderr and removes its entire owned workspace in `finally`. It does not use the default XDG index or mutate a real transcript to simulate incremental refresh. See the [benchmark procedure](tests/search-performance/README.md).
