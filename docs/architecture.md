# Architecture and privacy

The CLI captures environment, current directory, clock and IANA time zone once. Core functions receive a `Context` and explicit options. The Rust library is an implementation seam; the external compatibility boundary is [CLI JSON v1](json-protocol.md), not serialized internal models. There is no Python import API.

## Design rationale

The project centralizes format knowledge previously duplicated across ringleader, check-agent-logs and time-reconstruct. The November 2026 design replaced repeated raw-file searches with a disposable incremental index: the initial investigation reported an all-agent search taking minutes on 2026-11-15, superseding a September assessment based on a 3.5-second scan of a smaller corpus. These are historical motivations, not slimetrail performance measurements; see [measured results and limitations](performance.md).

Rust was chosen to reduce parsing and process-startup overhead. External consumers use versioned subprocess JSON, following ringleader's hooklinesinker integration model, so Python consumers need neither a stable Rust API nor platform-specific PyO3 wheels. Shared synthetic expected outputs constrain compatibility while Python readers coexist with the Rust implementation. [Integration boundaries and reference readers](integrations.md) describe the migration seam.

The initial alternatives review, dated 2026-11-15, found `@tangle-network/harness-sessions` lacked Cursor support and search/indexing; ATXF (`leostera/atxf`) addressed transcript exchange; and `coding_agent_session_search` and `agent-sessions` coupled their readers to application search stacks outside this project's scope. This records the original selection rationale, not a current capability survey. V1 uses SQLite FTS5 with synchronous refresh and literal/regex matching; fuzzy search, embeddings, a daemon and file watching remain outside scope.

The November 2026 first-indexing revision kept synchronous refresh and made it cheap and honest instead of replacing it. Its governing rule: a session the user remembers must never be silently missing from an exit-0 result, so every limit on coverage either makes the response incomplete (exit 1) or, for the deliberate `compact` coverage preset, carries an informational diagnostic. Rejected alternatives: time-budgeted partial results (silent first-use misses), a detached background build (agent sandboxes kill it), a pure scan without an index (does not work for database-backed stores) and a JSONL hybrid scan (its failure mode is silent exit-0 misses). The revision has three parts: keep-warm refreshes (trusted private snapshots, append-only transcript parsing, per-session Devin change keys, concurrent readers with one writer), indexing less (stored text separate from searchable text, one index-wide coverage) and an explicit build gate (per-agent estimates; small jobs build inline, larger ones prompt on a terminal or report `index_required`). OpenCode was deliberately left out of that revision: it still invalidates every session on any database change, and its 2.x tables are not read.

## Refresh and query lifecycle

`src/api.rs` opens one `IndexSession`, refreshes selected agents, then queries from the same session. Every session holds the non-versioned `lifecycle.lock` shared for its lifetime, so concurrent invocations read side by side. Opening first tries the lock exclusively, once and without waiting; only when that succeeds, so no other slimetrail process (including an older binary, which holds it exclusively) is running, does it prune older index files and remove legacy `staging/slimetrail-snapshot-*` and stray `staging/tmp-*` directories before taking the shared lock. Without a writer, the index database is opened read-only, and an index that does not exist yet reads as empty.

Writes need the exclusive `writer.lock`, a 0600 file with the same checks as the lifecycle lock. The refresh code takes it itself and holds it only for discovery and writes; the read-write connection exists only inside that guard, so no public method can write without it. With it held, the schema is created inside `BEGIN IMMEDIATE`, re-reading `user_version` in the transaction. Each refresh first increments the index-wide `settings.refresh_seq`, before it discovers anything, and each agent's finish records `published = generation` and the run's sequence number alongside its status. A query records `refresh_seq` at the start of each refresh, then waits up to 5 s for the writer lock. If it gets it and every selected agent was published by a refresh that started after that point, it skips its own refresh and reuses those runs' stored diagnostics; otherwise it refreshes. Either way it checkpoints the WAL best-effort (`TRUNCATE`), then opens a read transaction and pins its snapshot before releasing the lock, so all of its reads see one published state. A query that cannot get the lock in 5 s answers from the last published state inside one read transaction, with `incomplete: true` and a `refresh_in_progress` diagnostic. `slimetrail index` waits up to an hour, printing a note to stderr when it has to wait. `slimetrail index` and the library's `refresh_under_lease` do not pin a snapshot; only query refreshes do. Apart from that wait timing out, an index-busy error can only come from the 5 s shared `lifecycle.lock` wait at open, which an older binary holding the lock exclusively (or a session pruning old index files) can cause.

Each session stages its private snapshots in its own directory: it creates `staging/tmp-<random>/` (0700), creates and exclusively locks `owner.lock` (0600) inside it, then renames the directory to `staging/proc-<pid>-<random>/`. When the session closes, the directory is removed if it holds nothing but `owner.lock`; otherwise it is left for a later sweep. At open, a `proc-*` directory whose `owner.lock` can be locked belongs to a dead process and is removed; one without `owner.lock` is left alone. Different indexes have independent snapshot staging.

`src/sources/` discovers identities before emitting entries. Native header/row identity wins over a filename guess. Each `Entry` has a dense display index and a `source_id` based on a native identity plus emitted-item ordinal, or physical-record ordinal plus emitted-item ordinal. These are stable on unchanged reread and append, not across arbitrary rewrites. Parent provenance is optional when the store only establishes automation/subagent status.

Discovery includes native archives and child sessions. Codex discovery also reads the `<name>.jsonl.zst` rollouts Codex compresses when idle, decoding every zstd frame while reading; a plain `<name>.jsonl` beside one is the session and the compressed copy is ignored. Duplicate session identities prefer the live source, then newer source mtime, then deterministic path order. Every JSONL reader walks the shared ringleader archive and keeps only transcripts whose positive format marker names its own agent (Codex `session_meta`, Droid `session_start`, Pi `session`, Cursor untyped records with a top-level `role` and a `message` object, Claude message/title records), so one label folder can mix agents without mislabelling. An archived Cursor transcript reads its metadata only from the chat directory named after it (`<id>/meta.json`, `<id>/store.db`), so a Claude companion directory is never consulted as a Cursor chat. A file whose first identifying record is foreign but names no agent, or that is ambiguous/malformed, is diagnosed once, by the Claude reader (by the Codex reader for a compressed `.jsonl.zst`, which only Codex reads), and never attributed.

The index fingerprints file dependencies using device, inode, size, nanosecond mtime and ctime, including companion-file presence. Droid settings, Cursor metadata and database sidecars participate. Devin's fingerprint is a per-session change key, not file metadata. Codex title records are parsed once per observed title-file fingerprint into a shared immutable final-title map; later records, including empty titles, win. A Codex session's fingerprint covers its own transcript plus a hash of only its own final title from that map not the title file's stat, so a new thread appended to `session_index.jsonl` leaves every other Codex session reusable, and a rename invalidates only the renamed session. A title file that cannot be read is read once more; if that also fails, each session keeps the title hash from its cached fingerprint (sessions without one get an unavailable marker), so nothing is invalidated, and discovery adds one `source_unavailable` diagnostic for the agent. Malformed title records are likewise reported once per refresh as an agent-level `malformed_metadata` diagnostic, not on each session, so the run stays incomplete while they persist. Available root prefixes are canonicalized; missing or inaccessible suffixes retain their lexical identity. All roots are serialized and SHA-256 hashed into a namespace. Source availability is diagnosed only for selected agents, so an inaccessible unselected store does not abort healthy queries. Every source/session/entry/document relationship includes namespace and owning source, so identical IDs from different roots cannot mix. Namespace garbage collection is deferred; removing the index remains a full reset.

Refresh covers the selected agents before cwd/date/kind filtering. It discovers all of them first, keeping their snapshots, and estimates each agent's pending work (see [build estimates](performance.md#build-estimates)). A query refresh under a build limit admits agents smallest first while the total estimate fits, drops the other agents' snapshots, and leaves them unrefreshed with an `index_required` diagnostic; when no admitted agent has data and no gated agent was ever published, it fails with `IndexRequired` before writing anything. A whole-job limit (`BuildPolicy::Limit { whole: true }`, used by interactive CLI queries) fails with `IndexRequired` for every gated agent as soon as any agent is gated, whether or not it was published, so the CLI can prompt before anything is written; the writer-lock wait and an unfinished coverage rebuild still answer from the published state and never fail this way. `slimetrail index` admits everything. After each agent's ingest, the summed time of its successful source ingests (parse and write) and the bytes they parsed are added to the `throughput` table under the coverage the ingest ran at, when at least 1 MiB was parsed; a failed or churning source adds nothing, and a rejected append resume that fell back to a full parse counts the whole transcript. The coverage a build uses is decided in one place: the index's stored coverage once any agent has a published generation, any source is stored or a coverage rebuild is pending, and otherwise the caller's coverage, so the first build's coverage choice applies. Unchanged sources reuse parsed entries. Changed sources are reparsed one at a time, streaming into a transactional savepoint; a plain Claude, Codex, Droid or Pi transcript that only grew resumes where its last parse stopped (see append mode below). A source is reused only when its cached identity, dependency list and fingerprint equal the ones discovery just observed and discovery attached no private snapshot to it, since an attached snapshot is a reader's request to reparse; the live dependencies are not fingerprinted again. Database dependencies are trusted at ingest, because the private snapshot's acquisition checks are their consistency boundary. For the JSONL readers (Claude, Codex, Cursor, Droid, Pi) the live transcript, the first dependency, is still checked: it is stat'ed just before and just after the parse, and is stable only if its device and inode are unchanged and it either grew or kept the same size, mtime and ctime. A same-size in-place rewrite, a truncation, a replacement or a removal is a change. Cursor's transcript is checked even though its database is snapshotted. A change retries once, at the same source path or else at the rediscovered source of the same identity (so a Codex rollout decompressed mid-refresh is reread from its plain file); repeated churn rolls back and marks coverage incomplete. A transcript appended during its parse is stored as stable with the discovery-time fingerprint, so the next refresh picks up the rest. Stable malformed sources may publish their good entries with persistent diagnostics. Failed old rows are retained for recovery but excluded from current query results.

Append mode applies to uncompressed Claude, Codex, Droid and Pi transcripts. Each parse stores an append state with the source: the length of the transcript's complete, newline-terminated prefix, the SHA-256 of that prefix, its line, entry and malformed-line counts, the file's device and inode, a fingerprint of the companion files whose change forces a full reparse (Droid settings), and the session metadata as of that boundary. When a fresh or partial source with an append state is not reused, refresh hands the state to the reader. The reader opens the transcript once and resumes only if the device and inode match, the file is at least as long as the prefix, the prefix read through that handle hashes to the stored value, and the companion fingerprint is unchanged. It then parses only the tail and numbers entries after the stored count. The index deletes only the entries at or after that count and the native-title document, updates the session row in place, and writes the new state in the same savepoint. Any mismatch is rejected before an entry is emitted; the savepoint rolls back and the source is reparsed in full. A final line without a newline is parsed and indexed but left out of the state, so it is reread once completed. A final line without a newline that is not valid JSON is skipped while the file is less than 10 minutes old, and the source is stored as partial with no diagnostic; partial sources are never reused, so each refresh rechecks it until it is completed or old enough to count as malformed. This also applies to Cursor transcripts and, through the title index, to every Codex session parsed while the title index ends in such a line. Codex index titles are reapplied on every parse, so a title change resumes with no new bytes. Compressed `.jsonl.zst` rollouts and Cursor transcripts always reparse in full: Cursor's last entry takes a fallback timestamp from metadata and its `store.db` changes constantly.

Each agent's refresh generation is bumped, and persisted as incomplete, only after its discovery succeeds and before source changes commit. A discovery that fails outright leaves the generation and the visible sources untouched and records the failure diagnostics with status incomplete, so the previous state stays queryable with `incomplete: true`. A source is visible when its status is fresh or partial and its generation is at least its agent's last published generation, so a killed run never hides the rows it already replaced. A normal read comes after the process's own refresh (or a coalesced one) and therefore sees one published generation. A stale read, which is always exit 1, may also see sources that another live run has already replaced. Only complete discovery permits deletion of missing sources. When enumeration is incomplete, fresh and partial sources not seen in the run whose generation is at least the published one are moved up to the new generation at the end of the agent's run, so a source a partial inventory omitted stays visible. A restart refreshes again before querying, so interrupted ingestion does not silently present mixed generations as complete. Source modules receive cache metadata and never open the index.

## Index storage and search

The current file is `index-v3.sqlite3`, created with `auto_vacuum=INCREMENTAL` before any table and kept in WAL mode, so the `-wal` and `-shm` sidecars sit beside it. Every connection uses `synchronous=NORMAL` (corruption-safe in WAL, and the index is disposable), `foreign_keys=ON`, a 64 MiB `journal_size_limit` and a 30 s busy timeout. Schema/parser/search-normalization changes can require a new index version; this version is independent of JSON protocol version 1. A non-versioned `lifecycle.lock` covers all versions. Only exact recognized older index filenames and their sidecars are pruned, and only when no other slimetrail process holds the lifecycle lock; newer versions are preserved. Active databases are never unlinked or renamed.

Entries hold original text, which `read` and `entries` return in full. Each entry also records whether it is ordinary text, a tool result, or a duplicate (Claude's string `toolUseResult` repeating the same record's `tool_result`). That stored text is distinct from the searchable text. `src/index/coverage.rs::searchable_start` decides, per coverage, whether an entry is searchable and from which byte offset. A search document stores that offset as `text_start`, plus flags for non-ASCII/NUL data in the searchable slice `text[text_start..]`, but no copy of the text. Native titles produce one search document per session, with `text_start = 0`; derived titles do not. The FTS5 table is contentless (`content=''`, `contentless_delete=1`). The writer inserts the ASCII-lowercased slice into it directly, so the index holds trigram postings but no normalized copy of the searchable text. A delete trigger on search documents removes their postings, including for cascaded deletes. `verify_integrity` checks that documents and FTS rows have equal counts. It also recomputes a sample of 100 documents from entries and checks that each one's first trigram matches. The document child-key index includes entry index, avoiding growing per-session scans during deferred foreign-key checks.

Coverage applies to the whole index and is stored in the one-row `settings` table. A new index takes the configured coverage. After that, queries use the index's stored coverage even when the config differs. They never rebuild for coverage, and they say so in their coverage diagnostic. Only `slimetrail index` reconciles the index to the config. Under the writer lock, it first records `coverage_pending`. It then clears FTS with `'delete-all'`, deletes all search documents, and recreates them from stored entries and native titles, committing every 10,000 rows. Finally it sets `coverage` and clears `coverage_pending` in one commit, then runs `PRAGMA incremental_vacuum`. No transcript is reparsed. While `coverage_pending` is set, no refresh except the one completing the rebuild writes anything, including library refreshes without verification. Queries and those refreshes report a `coverage_rebuild_pending` diagnostic with `incomplete: true`, and query results may be missing matches because the search documents are partly rebuilt. The next `slimetrail index` restarts an interrupted rebuild from the beginning.

ASCII literal queries of at least three characters use a safely quoted trigram candidate query. Case-insensitive matching unions all non-ASCII documents into the candidates; both case modes union NUL-containing documents. Short, non-ASCII and NUL literals, and arbitrary regexes, scan indexed documents. Both paths verify, count and build snippets on the same searchable slice of the original text. Rust regex verification of that slice is the final authority, including Unicode simple case folding. There is no hand-maintained folding map or speculative regex prefilter.

Candidates stream in one global pass ordered by session/document. FTS rowids and indexed Unicode/NUL subsets form a union before original-text joins; eligible session keys and kind filters apply before text hydration, with native titles preserved. Fallback scans traverse the session index, reject ineligible keys and kinds before text hydration, and sort document order within each session; temporary text sorting is bounded by the largest accepted session rather than the whole eligible corpus. Ranked results remain bounded. Read pages stream entries but must visit the complete rendered session to calculate `total_chars`. Timeline selects event metadata only, retaining in-window events and missing-timestamp counts without loading entry text. See [performance](performance.md) for measured costs.

## Private SQLite snapshots

Original agent databases are **never opened through SQLite**, even with `mode=ro`: SQLite could create or modify native sidecars. Instead `src/sources/sqlite.rs` retains read-only OS handles for the DB/WAL and observes SHM/rollback-journal metadata. It captures all pre-copy identities and timestamps, then copies the DB and WAL with `std::fs::copy`, which tries an APFS clone (`fclonefileat`) on macOS and `copy_file_range` (a reflink on btrfs/XFS) on Linux. A copy whose length differs from the captured length is rejected as changed during copy. `fs::copy` reopens the source by path, so it is not tied to the retained handles; the post-copy check compares both the path's and the retained handles' identities and timestamps with the captured ones, which detects a replacement made before or during the copy. Length mismatches, replacements or churn reject the attempt; it retries once. Source SHM contents are never copied.

Accepted copies live in fresh 0700 directories under the session's own staging directory, with 0600 files. `fs::copy` carries the source's mode across, so each copy is set to 0600 immediately; the 0700 directory protects it in between. SQLite opens only the private copy read-write for WAL recovery, then enables `query_only`; its locks and sidecars stay private. Shared snapshot handles let all changed sessions from one backing database use the same accepted copy. Snapshots disappear after readers close. Startup removes only abandoned staging in that index's staging directory (see above), never global temporary directories.

Clean rollback-mode databases are supported; a nonempty rollback journal is rejected rather than attempting potentially unsafe recovery, including recovery involving original master-journal paths. This is metadata-validated quiescence, not an atomic OS snapshot or protection against adversarial metadata forgery. A continuously changing source can remain unavailable.

OpenCode and Devin always snapshot and enumerate their inventory, even on an otherwise unchanged refresh, then reuse unchanged entries. Cached sessions alone cannot prove complete inventory. A future shortcut requires a persisted completeness proof.

OpenCode keeps the whole-database rule: any change to its database reparses every session, because aggregate row counts or maximum timestamps are not sufficient evidence against same-size edits. Devin alone relaxes that rule. Its discovery reads a per-session change key from the snapshot in one pass: the session's `message_nodes` row count, maximum `node_id` and maximum `rowid`, plus its `sessions` row (title, working directory, creation time, `last_activity_at`, `main_chain_id`); a subagent child `ID/AGENT` uses its parent's key plus its `subagent_heads` `chain_node_id` and `updated_at` when that column exists. The source fingerprint is the SHA-256 of that key, so only sessions whose key changed get the snapshot and are reparsed. Each Devin parse also stores a content hash in `sources.state`, covering every `message_nodes` column the parse reads for the rows it loads plus the `sessions` row and, for a child, its head row. Query refreshes trust the change key. `slimetrail index` additionally recomputes the content hash of every session it would otherwise reuse and reparses any whose hash differs, so an in-place edit that leaves the change key unchanged is picked up only by `slimetrail index`.

## Security boundary

The index contains private session data and possibly secrets. Index directories must be 0700 and files, locks and journals 0600. Existing insecure, symlink or multiply linked index files are rejected. Canonicalized paths reject source/index overlap in either direction. Discovery avoids recursive symlink traversal into unrelated stores. Core diagnostics omit entry text, but ordinary query output intentionally includes transcript data and identifiers.

Tests use synthetic fixtures. The opt-in real benchmark uses a separate private repo-local index, emits only aggregate metrics, discards search stdout, sanitizes stderr and removes its entire owned workspace in `finally`. It does not use the default XDG index or mutate a real transcript to simulate incremental refresh. See the [benchmark procedure](tests/search-performance/README.md).
